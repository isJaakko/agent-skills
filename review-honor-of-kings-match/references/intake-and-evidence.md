## 1. 输入清单

把输入分为必要项和增强项，不要一次追问全部增强项。

### 必要项

- 录像或可访问的视频文件/链接；
- 录像倍速：固定 `1×`、`2×`、`4×` 等，或变速/含暂停与剪辑；
- 游玩分路；
- 游玩英雄；
- 用户希望回答的核心问题。

### 增强项

- 模式、段位/训练水平、单排或组排；
- 评分主体所在队伍或队伍颜色；
- 对局日期、客户端版本或赛季；
- 赛后结算面板、出装/铭文、经济曲线；
- 用户当时的意图、队内语音或信号约定；
- 网络波动、设备卡顿。

若录像倍速、游玩分路或游玩英雄任一缺失，先用一个合并问题索取三项并等待，不得用画面识别结果代替用户确认。整队复盘允许把英雄与分路记录为“整队 / 不指定”。其余缺失项写入“证据与限制”，并继续处理可见内容。

## 2. 证据等级

为关键事件和结论标记置信度：

- **A / 高**：画面、HUD、赛后面板或连续视频直接显示；时间和主体明确。
- **B / 中**：由两个以上可见迹象合理推断，例如小地图动向、血量变化与击杀播报相互支持。
- **C / 低**：单一模糊迹象、被遮挡画面或用户回忆，尚不能独立验证。
- **未知**：录像未覆盖、画质不可读或视角不允许判断。

报告中的事实可以直接陈述；推断使用“更可能”“从画面看”“若当时……则……”等限定语。不要把用户意图当作画面事实，也不要因用户自述与画面不一致就直接否定用户；并列记录差异。

## 3. 阵容与英雄身份识别及强制确认

阵容身份是所有阵容、对位与团战结论的前置条件。先完成身份核验，再统计“几射手、几前排”、伤害构成、控制链或胜负条件。

### 3.1 证据优先级

按以下顺序识别每个英雄：

1. **用户明确提供或纠正的英雄身份**：记为 `用户确认`，并保留在证据说明中。
2. **画面中的英雄名称文字**：优先读取载入页、局内战绩页、选将页或结算页中的明确英雄名。
3. **独立的局内交叉证据**：局内队伍名单、玩家昵称映射、技能图标与效果、模型、装备路径、结算页头像与名称对应关系。
4. **头像、皮肤立绘或模型印象**：只能作为辅助，不得单独作为确定英雄身份的依据。

读取载入页时，先保留完整画面，再分别放大十个玩家卡片。区分英雄名、皮肤名或称号、玩家昵称、战队名；画面中出现文字不等于该文字就是英雄名。OCR 结果只是候选文本，必须回看画面核对易混字和文字所属区域。

`--clock-ocr` 只负责局内时钟，不代表已经完成阵容文字识别。阵容识别需要对载入页或其他名单画面单独取帧、放大和核对。

### 3.2 逐槽记录

双方每个位置建立一条记录，至少包含：

| 字段 | 内容 |
|---|---|
| 队伍与槽位 | 我方/敌方；载入页从上到下或从左到右的位置 |
| 玩家昵称 | 可见则记录，用于跨画面映射 |
| 英雄文字 | 画面直接读到的英雄名；不可读则写未知 |
| 辅助线索 | 头像、皮肤、模型、技能或装备表现 |
| 交叉验证 | 局内名单、战绩页、结算页或用户确认 |
| 置信度 | 高 / 中 / 低 |

不要因为常规模式通常不重复英雄，就擅自删除或替换一个看似重复的识别结果；应继续依据队伍颜色、玩家昵称和其他画面核对。

### 3.3 置信度与报告措辞

- **高置信度**：清晰英雄名文字并有一项独立交叉证据，或用户明确确认。可以作为事实写入报告。
- **中置信度**：英雄名文字部分可读但仍有歧义，或存在两项相互支持的视觉线索。写明识别依据与不确定性。
- **低置信度**：仅有头像、皮肤、模型印象或一张模糊单帧。统一写 `待用户确认（候选：A / B）`；没有可靠候选则写 `待用户确认`。

不得用低置信度身份作确定性的阵容优劣、对线克制或评分依据。无论是否存在低置信度项，完整复盘都必须经过下述阵容确认关卡。

### 3.4 强制阵容确认关卡

身份识别完成后，先单独向用户展示一张阵容确认卡，至少包含：

| 队伍/槽位 | 识别英雄 | 推定分路或职责 | 主要依据 | 置信度 |
|---|---|---|---|---|
| 我方 1 |  |  | 载入页文字 / 战绩页 / 结算页 / 用户提供 | 高 / 中 / 低 |
| 敌方 1 |  |  | 载入页文字 / 战绩页 / 结算页 / 用户提供 | 高 / 中 / 低 |

补齐双方十个槽位。英雄身份与分路是不同字段：英雄可以高置信度，但分路仍可能只是推定。中低置信度英雄统一写 `待用户确认（候选：A / B）` 或 `待用户确认`。

确认卡后只提出一个问题，例如：“请确认以上双方阵容与分路是否正确；如有错误，请直接指出英雄或位置。”随后停止当前轮次并等待用户回复。十名英雄均为高置信度、与常见分路一致或能从结算页交叉验证，都不能成为跳过确认的理由。

状态只有两种：

- `待确认`：已展示确认卡，但用户尚未明确确认完整阵容；不得继续阵容优劣、伤害结构、对位克制、胜负条件、事件归因、评分或完整报告。
- `已确认`：用户明确表示完整阵容正确；才可进入深度复盘。

用户指出错误时，更新对应槽位和证据来源，重新展示完整确认卡并再次等待确认。不得只确认被纠正的单个英雄后直接继续，也不得通过“假设 A/B 都成立”的条件式分析绕过这一关卡。

### 3.5 确认后才能使用的阵容结论

阵容状态为 `已确认` 后，才可分析以下内容：

- 阵容职业构成，例如“三射手”与“双射手加法师”；
- 物理/法术伤害占比和出装建议；
- 核心控制链、开团点、前排数量或保护能力；
- 用户的关键对位与团战职责；
- 阵容维度评分。

### 3.6 用户纠正后的传播规则

用户纠正任何英雄身份后，立即将其作为 `用户确认`，并重新检查所有依赖该身份的内容：

1. 双方完整阵容与职业数量；
2. 对线关系和装备建议；
3. 前中后期胜负条件；
4. 开团、反手、保护和输出职责；
5. 团战、转折点解释与各维度评分；
6. 最终优先改进项。

受错误身份影响的旧结论必须明确撤回或改写，不能只替换英雄名字而保留原分析。

## 4. 视频时间与游戏时间

同时维护两种时间：

| 字段 | 含义 | 示例 |
|---|---|---|
| 视频时间 | 文件从开头开始的时间，用于定位帧或片段 | `09:17.5` |
| 游戏时间 | 游戏 HUD 显示的对局时间，用于分析节奏 | `08:42` |

录像有加载界面、暂停、倍速、拖动或剪辑时，二者不会稳定相减。至少为每个关键事件记录一个游戏时间；无法读取时只保留视频时间并标记未知。

把用户声明的倍速作为取证参数，而不是精确时间换算的唯一依据。固定 `2×` 录像中，1 秒视频通常覆盖约 2 秒游戏过程；若希望每 1 秒游戏过程抽一帧，可先用约 0.5 秒的视频抽帧间隔。变速录像按区段记录倍速，并在倍速切换点重新建立时间锚点。

先找 3 个以上锚点（例如首个清晰 HUD 时间、资源播报、结算前时间），检查映射是否连续。若发现跳变，把录像分成多个映射区段。

### OCR 局内时间

运行取证脚本时使用 `--playback-speed <倍率> --clock-ocr`。脚本会：

- 默认扫描画面顶部中央的归一化区域 `0.25,0,0.5,0.18`；
- 在 macOS 使用原生 Vision，在其他已安装环境使用 Tesseract；
- 输出 `clock-roi-preview.jpg` 供 ROI 校准；
- 输出 `clock-map.tsv`，记录视频时间、OCR 原文、原始/稳定化局内时间、置信度、状态和分段；
- 把可用局内时间写回 `manifest.json` 的每个帧记录。

ROI 坐标按左上角归一化，依次为 `x,y,width,height`。预览未覆盖计时器时，用 `--clock-roi X,Y,W,H --force` 调整后重跑。

按以下方式解释 `clock-map.tsv` 状态：

| 状态 | 含义 | 使用方式 |
|---|---|---|
| anchor / accepted | OCR 达到阈值且符合时间连续性 | 可作时间锚点；关键事件仍需目视抽查 |
| interpolated | 位于同一分段的两个可靠锚点之间 | 作为估算时间，标为中等置信度 |
| discontinuity-anchor | 后续读数确认发生暂停、跳转、剪辑或倍速变化 | 从此处开始新映射分段 |
| low-confidence | OCR 读数低于阈值 | 不直接用于关键结论 |
| needs-review | OCR 读数与倍速/相邻锚点冲突 | 人工查看源帧后决定 |
| missing | ROI 中未识别到合法 `MM:SS` | 仅保留视频时间 |

连续性通过的 OCR 默认作为 B 级机器证据；关键事件经源帧目视确认后才提升为 A 级。不得把插值时间写成画面直接可见的精确事实。

若 macOS Vision 对所有帧返回失败，可能是系统 OCR 服务被沙箱隔离；在获得必要本地执行许可后重跑同一命令。若 OCR 覆盖率低但无系统错误，先检查 ROI、分辨率和 HUD 遮挡，不要自动降低阈值以制造读数。

## 5. 三遍取证方法

### 全局遍

以约 5–10 秒间隔浏览概览帧或倍速观看，标记：

- 击杀、死亡、推塔、资源、回城和换线；
- 经济/等级领先变化（仅记录可读数据）；
- 评分主体的长距离移动和长时间离线；
- 疑似团战起点与结束点；
- 可能改变胜率走势的决策。

此遍只形成候选事件，不下最终微操结论。

### 事件遍

对以下窗口按 0.5–1 秒连续帧或正常速度复看：

- 每次死亡前至少 15–20 秒，死亡后直到直接后果明确；
- 重要中立资源出现/争夺前后至少 45 秒；
- 团战触发前至少 20–30 秒，结束后直到资源转化完成；
- 高影响回城、换线、带线、越塔、追击或撤退决策。

微操判断需要连续画面；概览联系表仅用于定位。

### 主体遍

连续追踪评分主体：

- 当时可见的小地图信息；
- 兵线位置、最近可获得的安全经济和回城窗口；
- 血量、蓝量、关键技能、装备格和相对经济（可见时）；
- 与队友、敌人的距离和行动同步；
- 选择该路线或战斗的机会成本。

只使用主体当时能获得的信息评价决策，不把后续揭示的草丛敌人位置倒灌回先前判断。

## 6. 事件台账

使用脚本生成的 `event-ledger.tsv`，每行记录一个原子事件：

| 字段 | 填写规则 |
|---|---|
| video_time | 文件时间；无法定位时留空 |
| game_time | HUD 时间；优先使用已目视确认的 OCR 锚点，无法读取时留空 |
| phase | 对线/转线/中期/后期等，不硬编码固定分钟 |
| event_type | death/objective/teamfight/rotation/recall/tower/other |
| actors | 涉及英雄或队伍 |
| observed | 仅写直接观察，不先写评价 |
| inferred | 写推断及依据，可留空 |
| consequence | 直接结果与后续资源转化 |
| confidence | A/B/C/unknown |
| follow_up | 需要高密度复看的窗口或待确认问题 |

将“事件发生”与“为什么发生”拆成不同字段，可减少第一印象偏差。

## 7. 低质量与缺失信息处理

- 画质不足以读经济/技能时，改用相对状态和位置证据，不写精确差值。
- 只有单一玩家视角时，不评价其视野外队友的精确技能顺序。
- 录像不含选人阶段时，用开局阵容反推职责，但不臆测 BP 过程。
- 录像被剪辑时，不输出完整时间线覆盖率；明确列出缺口。
- 片段不足以覆盖某评分维度时写 `N/A`，不要用默认 5 分填补。
- 若语音缺失，把“没有沟通”改写为“录像无法验证沟通”。

## 8. 版本信息处理

英雄强度、装备属性、地图机制、野怪名称和刷新规则会变化。需要版本事实时：

1. 先从用户、录像界面或文件日期确定大致版本；
2. 优先核验官方更新公告或同版本可靠资料；
3. 在报告中注明版本依据和检索日期；
4. 无法确认时，分析稳定概念（兵线优先、人数差、状态差、技能窗口），并对具体数值使用条件式表述。

不要因为查不到版本就停止整局复盘；只降低版本敏感部分的置信度。
