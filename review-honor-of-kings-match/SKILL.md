# 王者荣耀对局复盘

## 核心原则

- 先取证，后归因，再评分。把每个重要判断绑定到游戏时间或视频时间。
- 分开记录 `视频时间` 与 HUD 显示的 `游戏时间`。录像可能有剪辑、暂停或倍速，不得默认二者恒定对应。
- 区分三类信息：`事实`（画面直接可见）、`推断`（由多个迹象支持）、`用户补充`（尚未由画面验证）。
- 英雄身份先验证，后分析。可读的英雄文字与用户明确确认优先于头像、皮肤和模型印象；仅凭头像或单帧模糊画面不得把英雄名称写成事实。
- 双方阵容确认是完整复盘的强制关卡。无论自动识别置信度高低，都必须先展示双方十人名单并等待用户明确确认；确认前不得输出阵容优劣、对位结论、评分或完整复盘。
- 对看不清的经济、技能冷却、装备、信号或沟通标记为“未知”，不得补造精确数据。
- 避免结果论。分别评价决策质量、执行质量和结果；失败的正确决策与成功的冒险决策不能只按结果评分。
- 把个人责任与团队责任拆开。只把当时该玩家可观察、可控制的部分计入个人评分。
- 把英雄数值、装备、野怪名称、刷新时间、地图机制和版本强度视为版本敏感信息。需要据此下结论时，先确认对局日期/版本并用可用的最新可靠来源核验；无法核验时明确使用条件式表述。

## 确认复盘对象

开始查看录像或评分前，一次性让用户提供以下三项必填信息：

1. **录像倍速**：固定 `1×`、`2×`、`4×` 等，或变速/含暂停与剪辑；变速时尽量说明区段。
2. **游玩分路**：对抗路、打野、中路、发育路、游走，或实际承担的特殊分工。
3. **游玩英雄**：用户操控的英雄名称。

缺少任一项时，用一个简短问题合并询问并等待补充；不要从画面猜测后跳过确认。若用户明确要求整队复盘，英雄与分路可分别记录为“整队”和“不指定”，但仍须提供录像倍速。

取得三项必填信息后，再确认队伍颜色，并收集对局模式、段位/水平、对局日期或版本、用户关注点，以及可选的赛后面板、出装/铭文、语音沟通、当时意图和网络/设备问题。非必填信息缺失时继续分析并列入限制，不要用一串问题阻塞工作。

## 选择复盘模式

- **指定玩家模式**：输出个人七维评分，并补充团队环境对其决策的影响。默认使用此模式。
- **整队模式**：以队伍为评分主体，分析五人协同；不要给未知个人分配责任。
- **片段模式**：只评价片段覆盖的维度，未覆盖项写 `N/A`，不得外推整局总分。
- **低证据模式**：画质、视角或时长不足时，优先输出可确认事实、待确认问题和补充材料清单，不强行给精确分数。

## 工作流

### 1. 建立录像证据包

先完整阅读 [references/intake-and-evidence.md](references/intake-and-evidence.md)。

对本地视频，优先运行：

```bash
python3 scripts/extract_replay_evidence.py /path/to/match.mp4 \
  --output /path/to/evidence --playback-speed 2x --clock-ocr
```

脚本依赖 `ffmpeg` 和 `ffprobe`，会生成概览帧、联系表、焦点窗口帧、`manifest.json`、`event-ledger.tsv` 和 HUD 局内时间映射 `clock-map.tsv`。macOS 默认使用原生 Vision OCR，其他环境可使用 Tesseract。根据用户声明的录像倍速调整浏览和焦点抽帧密度；倍速越高，同一视频秒数包含的游戏过程越多。若环境已有可靠的视频逐帧能力，也可直接使用，但仍须遵守同一证据协议。

检查 `clock-roi-preview.jpg` 是否只覆盖顶部计时 HUD。默认 ROI 为顶部中央 `0.25,0,0.5,0.18`；位置不符时用 `--clock-roi X,Y,W,H --force` 重跑。检查 `clock-map.tsv` 中的置信度、连续性状态和分段；关键事件的 OCR 时间必须回看画面确认。若 macOS Vision 在沙箱中对所有帧失败，在取得相应本地执行许可后重跑同一命令，不要静默伪造或只按倍速换算时间。

首次粗看后，对死亡、资源争夺、团战和转折点补抽高密度窗口；`--focus` 使用视频时间而非游戏 HUD 时间：

```bash
python3 scripts/extract_replay_evidence.py match.mp4 --output evidence \
  --focus 08:10-08:35 --focus 13:40-14:15 --focus-step 0.5 --force
```

不要用稀疏概览帧评价连招、走位或技能先后；微操结论必须查看正常速度视频或高密度连续帧。

### 2. 识别并强制确认双方阵容

先按 [references/intake-and-evidence.md](references/intake-and-evidence.md) 的“阵容与英雄身份识别”逐槽建立双方 10 人名单，再记录分路、召唤师技能/出装（仅在可见时）、胜负、总时长和评分主体。

- 优先读取载入页、局内战绩页或结算页中的英雄名称文字；头像、皮肤、模型与技能特效只作为辅助证据。
- 每个英雄都记录识别依据和置信度。仅有头像或模糊单帧支持时，写 `待用户确认（候选：A / B）`，不得直接定名。
- 用局内名单、玩家昵称映射、技能表现或结算页至少交叉验证一次。不要把皮肤名、称号或玩家昵称误当成英雄名。
- 识别完成后，先单独输出“阵容确认卡”：逐槽列出双方英雄、推定分路/职责、主要识别依据与置信度；中低置信度项明确标为 `待用户确认`。
- 在确认卡后只问一个简短问题，请用户确认或纠正双方阵容，然后停止当前轮次并等待。即使十名英雄均为高置信度，也不得跳过此步骤。
- 用户纠正后，更新所有受影响槽位，再展示完整确认卡并等待用户确认。只有用户明确表示阵容正确后，才将状态记为 `已确认` 并继续后续分析。
- 阵容处于 `待确认` 时，不得输出阵容优劣、职业构成、伤害结构、对位克制、胜负条件、相关评分或完整复盘，也不要用条件式分支绕过确认关卡。

### 3. 建立对局基线并分析阵容

仅在阵容状态为 `已确认` 后开始阵容分析。完整报告必须包含独立的“双方阵容分析结论”章节，不能只复述英雄名单，也不能把阵容分析压缩进一两句团战说明。

按 [references/analysis-and-scoring.md](references/analysis-and-scoring.md) 的阵容分析验收结构完成以下产物：

- 双方能力对照：主要开团、反开、保护、前排、爆发、持续输出、突进与带线来源；
- 双方在阵地战、河道窄口、开放区域、遭遇战和分带中的相对优劣；
- 各自胜利条件、应避免的战斗形态、关键窗口、关键对位和资源优先级；
- 一段明确的总体对阵结论，说明哪一方希望怎样打，以及原因；
- 评分主体的职责、安全站位、理想入场条件和禁区；
- 至少两个本局时间戳，验证阵容理论如何在实战中兑现或失效。

若录像不足以验证某个阵容判断，将其标为理论推断并降低置信度，但不能省略上述阵容分析结构。简版报告也必须保留总体对阵结论、评分主体职责和至少一条实战证据。

阵容分析评价的是“理解与执行阵容条件”，而不是仅评价选出的英雄强不强。

### 4. 执行三遍复盘

1. **全局遍**：快速通看整局，标记阶段变化、击杀、推塔、资源、回城、换线和疑似转折点。
2. **事件遍**：逐一复看所有死亡、重要资源前后 45 秒、关键团战前中后及高影响决策。
3. **主体遍**：持续追踪评分主体的兵线、经济相对位次、位置、可见信息、技能/状态、决策选项与机会成本。

同步维护事件台账。先记录观察，再写原因；不要在第一遍就锁定结论。

### 5. 完成模块分析

分析和评分前完整阅读 [references/analysis-and-scoring.md](references/analysis-and-scoring.md)。必须覆盖：

- 阵容与胜利条件；
- 对线、补经济、回城、换血、支援和转线；
- 中立资源、兵线优先权、区域占位和资源置换；
- 每次死亡的近因、根因、可避免度与机会成本；
- 关键团战的准备、入场、目标、技能、站位、撤退和后续转化；
- 3–5 个高影响转折点及可行替代方案；
- 七维评分、总分、置信度和改进优先级。

### 6. 形成建议

把建议写成可训练的行为，不只写“注意意识”或“多看小地图”。每条建议包含：

- **触发器**：什么局面出现时执行；
- **动作**：具体做什么；
- **理由**：解决本局哪个重复问题；
- **成功指标**：下一局如何判断做到了。

优先给 3 个最高杠杆改进项，再给训练法与下一局检查清单。建议必须能追溯到至少一个录像证据；通用技巧需标为补充而非本局结论。

### 7. 输出复盘报告

完整阅读 [references/report-template.md](references/report-template.md)，按其结构输出。默认使用用户的语言，中文请求使用简体中文。保持时间戳可点击或易定位，例如 `游戏 08:42（视频 09:17）`。

若用户要求简版，仍保留：结论摘要、双方阵容分析结论、评分主体阵容职责、至少一条阵容实战证据、关键时间线、七维评分、前三改进项和证据限制。

## 完成前质检

- 确认逐槽核对双方阵容，并让英雄文字证据优先于头像判断。
- 确认曾向用户展示完整阵容确认卡，且在用户明确确认前没有进入阵容结论、对位分析、评分或完整报告。
- 确认最终报告中的阵容确认状态为 `已确认`；若仍为 `待确认`，只能停留在阵容确认卡与确认问题。
- 确认无法确定的英雄明确标成 `待用户确认`，没有基于低置信度身份下强结论。
- 若用户纠正了英雄，确认已同步更新阵容、对位、胜负条件、团战职责、评分与建议。
- 确认报告有独立的“双方阵容分析结论”，而非只有英雄名单或职责摘要。
- 确认双方能力对照、总体对阵结论、评分主体职责均已输出，并以至少两个本局时间戳连接阵容理论与实战。
- 上述阵容分析产物任一缺失时，报告视为未完成；补齐后才能输出最终评分与结论。
- 确认每个低分项至少有一条具体证据，高影响结论尽量有两条互相支持的证据。
- 确认每次死亡都分析死亡前决策，而非只描述死亡瞬间。
- 确认每次资源得失都检查兵线、人数、状态、关键技能、提前站位和可接受置换。
- 确认团战分析覆盖“战前—战中—战后”，并拆分决策与执行。
- 确认转折点具有可行的反事实方案，而非事后要求玩家使用当时未知的信息。
- 确认各维度评分使用同一量表，`N/A` 不计入总分，并显示评分置信度。
- 确认建议具体、可练、可衡量，且没有把队友不可控行为算作个人改进项。
